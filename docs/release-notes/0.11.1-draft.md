# PowerIO 0.11.1 release notes

PowerIO 0.11.1 is the first compatible fix release of the 0.11 line. Nothing in
the public Rust API or C ABI 7 changes shape; every addition is a new function,
a new C entry point, or a new optional argument. PowerIO IR advances to generation 3 for the new LinDist3Flow value types.
This build reads generations 2 and 3; PowerIO 0.11.0 reads generation 2 only.
The published generation-2 schema remains unchanged.

## Named axes for the DC calculations

Every DC calculation shares one bus axis and one branch axis, and 0.11.1 names
them in every language. In Rust, `DcOperators::build_with` takes
`DcOperatorOptions`, and `branch_rows`, `branch_identities`, and
`skipped_branch_rows` sit beside `bus_ids`: the branch axis is every in service,
non self loop branch in table order, with three winding transformer windings
after the branches. With `skip_zero_impedance`, a zero impedance branch leaves
the axis and is listed instead of failing the build with
`BUILD.OPERATOR.ZERO_IMPEDANCE`, the same choice the admittance builders already
offered.

C ABI 7 gains the `PioDcOperators` handle: `pio_calc_dc_operators` builds the
operators once, the axis accessors name both axes, and the eight calculations
run over the handle. The existing `pio_calc_*` entry points are unchanged.
Python exposes `calc_dc_index_map` and `skip_zero_impedance` on every DC
`calc_*` method, and the MCP `calc_matrix` tool reports `row_ids` and `col_ids`
for every result, serves the eight DC calculations by name, and takes
`skip_zero_impedance`. PowerIO.jl 0.11.1 binds the handle as
`calc_dc_index_map`. The change comes from the PowerIO.jl port of PowerDiff.jl
(eigenergy/PowerIO.jl#139 and #140).

## Operating points as networks

`powerio::network_with_operating_point` and Python `OperatingPoint.network`
return the balanced network an operating point states, with the point's
values applied to a copy. A consumer selects a collection entry and hands it to
a solver without emitting and reparsing it; the MCP `summarize` and
`calc_matrix` tools accept an operating point entry through that network.

## Diagnostics and OpenDSS geometry

MCP diagnostic records carry `suggested_action`, `related`, and `details`
beside the code, severity, message, target, id, and spans. The OpenDSS
geometry regression cases from Burhan Abdullah's draft (#480) run as ordinary
tests: a geometry defined line is reported by `READ.DSS.GEOMETRY_UNRESOLVED`
when it is read and never receives the OpenDSS factory impedance or a
fabricated conductor count (#479).

## Multiconductor LinDist3Flow

`LinDist3FlowOpfInstance` describes a radial, fixed-reference approximation over
`MulticonductorNetwork`. Separate neutral Kron projection records its
assumptions and current-recovery coefficients, and rejects finite current
limits on eliminated neutrals. Sparse affine and conic preparation stays in
`powerio-matrix`; solver selection remains with the consumer.

C, Python, and Julia expose typed instances and solutions, physical node and
conductor axes, reference voltages, and solution columns in SI units. The
supported feeder assumptions and deferred equipment are documented in the
multiconductor LinDist3Flow design note. Generation 3 records the new types;
the reader rejects those types if a document declares generation 2.
